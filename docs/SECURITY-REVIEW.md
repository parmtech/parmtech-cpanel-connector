# Focused security review: recovery and rotation

This is a focused engineering review, not an independent audit or a claim of public multi-user readiness. It covers the recovery and key rotation changes, login CSRF checks, rate-limit configuration and the isolated setup flow.

- Recovery requires a verified email, a short-lived code and the original browser's random binding. Challenge hashes incorporate that binding. Codes expire after 15 minutes and allow five attempts. Requests are limited per email in PostgreSQL as well as by a process-local IP limit. Responses use generic wording, but delivery and timing differences can still reveal account existence; dedicated anti-enumeration and abuse controls are needed before public use.
- A successful reset changes the password and deletes the user's existing sessions, OAuth access/refresh tokens and outstanding authorization codes in one transaction, without deleting hosting profiles. Existing in-flight requests or concurrently created sessions/grants are not guaranteed to be interrupted. An incident response should also revoke hosting tokens at the provider and investigate server access.
- Login and signup forms now reject a missing CSRF cookie rather than accepting two absent values. The MCP IP fallback uses the rate limiter's IPv6 normalization. The SDK host allowlist uses hostnames rather than host:port, fixing non-default port setups. Limits remain process-local except recovery's per-email limit; use one instance and add durable shared abuse controls before scaling.
- Database key rotation is offline and transactional for account rows. Configuration and external encrypted files cannot be switched atomically with the database; see [the rotation procedure](KEY-ROTATION.md), including the certificate-renewal and owner-import constraints. The server operator can decrypt stored credentials. Database or key compromise requires a broader incident response than rotating the encryption key.
- Isolated tests cover PostgreSQL setup and recovery, replay, browser binding, wrong attempts, expiry, session/token removal, account preservation, wrong-key rollback, and the HTTP setup/recovery flow using local fixture SMTP. They do not prove external mail delivery, public reverse proxy behaviour, production traffic, concurrent active-session revocation, or acceptance against a real cPanel or WHM account. Dedicated cPanel/WHM testing and independent review remain open.

## Repeating the tests

Use a dedicated disposable PostgreSQL database, never a production database. `npm test` runs the existing mock and local checks. Set standard `PG*` variables for that test database and run `npm run test:setup-db` and `npm run test:security-db`; both create and drop a uniquely named test schema. For the full local HTTP and fixture SMTP check, set `PCC_TEST_DATABASE_URL` to that isolated database and run `npm run test:setup-http-db`. The HTTP check starts a local app and SMTP fixture and creates and drops its own schema. It never contacts a real hosting account.
